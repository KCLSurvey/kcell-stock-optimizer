## Р-019 · Двойное местонахождение: учётное и фактическое

| Поле | Значение |
|---|---|
| **Дата** | 26.07.2026 |
| **Инициатор** | Владелец проекта |
| **Решение** | Экземпляр хранит **два местонахождения одновременно**: учётное из финансовой системы и фактическое из наблюдений. Продукт не переписывает учётное, а показывает оба и измеряет разрыв. Введён показатель **лаг документов** |
| **Обоснование** | Оборудование перемещается по учётной цепочке документами, а не физически. Подрядчик получил, вывез, смонтировал — а акт не подписан; в учёте материал всё это время на складе подрядчика. Это порождает две проблемы: планировщик видит остаток, которого нет, и оборудование не переводится в основные средства, хотя работает. Дисциплиной это не лечится: документооборот отстаёт по процессу |
| **Механизмы получения факта** | (1) Заказ на работу с материальным листом: бригада выбирает номер заказа, система подтягивает перечень, бригада фотографирует выгрузку с геопривязкой. (2) Сигнал о включении в работу из сетевой системы: не требует действий подрядчика |
| **Влияние** | Мемо §2.3 и §4.5, архитектура §3.5, модель данных §1.3 и §1.11, модули М2.6.1–М2.6.2 и М3.1.1–М3.1.4, визуализации §4. Добавлен разрыв Р4 |
| **Статус** | Принято |

## Р-020 · Граница по дате внедрения для пассивной инфраструктуры

| Поле | Значение |
|---|---|
| **Дата** | 26.07.2026 |
| **Инициатор** | Владелец проекта |
| **Решение** | Классы В и Г (несерийная и расходная номенклатура) разделяются на **унаследованные** — смонтированные до внедрения — и **новые** — выходящие со склада после. Корректный учёт гарантируется для новых с первой версии; унаследованные восстанавливаются выборочно в фазе 3 и позже |

| **Механизм для новой** | **Проектная спецификация планировщика** после обследования локации становится материальным листом и ожидаемым составом площадки. Общий норматив «штук на площадку» остаётся только там, где спецификации нет |
| **Влияние** | Мемо §7.1, модули §4.2, модель данных §1.12, устав §3.2, дорожная карта §2.2, риск Т14 |

## Р-023 · Смысл в одном выражении и двойное имя продукта

| Поле | Значение |
|---|---|
| **Дата** | 27.07.2026 |
| **Инициатор** | Владелец проекта |
| **Решение** | Смысл проекта формулируется как **CapEx Velocity — сокращаем время и потери на пути от денег до работающего оборудования**. Главный показатель — **капитал под риском в днях** (Capital-at-Risk Days) = средний объём капитала вне эксплуатации × среднее число дней вне эксплуатации + безвозвратные потери за период. Продукт носит **два имени**: «Сквозной учёт» для оператора и рынка Казахстана и СНГ, CapEx Velocity для инвестора и международного рынка |
| **Обоснование** | Проект содержит два независимых эффекта — задержку и утечку. Формулировка, покрывающая только один, занижает продукт примерно вдвое. Показатель «деньги × дни» переводится в стоимость капитала одним умножением и потому защищаем на инвестиционном комитете, в отличие от процентов точности учёта. Русское имя описывает механику и понятно бухгалтерии без перевода; английское описывает результат в терминах, которыми инвестор считает деньги |
| **Отклонённые альтернативы** | «Ускорение оборачиваемости капекса и опекса» — капитальные и операционные расходы суть потоки затрат, они не оборачиваются; оборачивается запас. Смешение категорий обесценивает остальные цифры документа. «Ускорение оборачиваемости оборудования» — строго корректно, но покрывает только скорость, теряя потери и списания. «Улучшение индекса здоровья оборотного капитала» — индекс есть метрика продукта, а не ценность клиента; уместен в дашборде, не в позиционировании. Полное переименование продукта — ломает Р-005 и требует правки всех файлов без выигрыша |
| **Влияние** | Мемо шапка, §1.1–1.3, §5.2, источники · one-pager шапка и первый блок · README · глоссарий · `00_Управление/Понятия/CapEx_Velocity.md` и `Капитал_под_риском_в_днях.md` |
| **Статус** | Принято |

## Р-024 · Оси выбора вместо плоского списка вариантов; рекомендация С0 → С1 → С2

| Поле | Значение |
|---|---|
| **Дата** | 27.07.2026 |
| **Инициатор** | Владелец проекта (постановка), архитектор (форма) |
| **Решение** | Пространство стратегического выбора описывается **пятью осями** (А способ создания · Б охват жизненного цикла · В зрелость клиента · Г коммерческая конструкция · Д источник правды) и **пятью сценариями** как комбинациями позиций. Ось В признана не развилкой, а параметром архитектуры. По оси Г принимается позиция Г2 (платная диагностика) с переходом в Г1 (подписка). Рекомендуемая последовательность — **С0 Диагностика → С1 Клин достоверности → С2 Сквозной контроль** |
| **Обоснование** | Исходный список из шести «вариантов» смешивал четыре разные сущности — развилки, сценарии, конфигурации внедрения и фазы, — из-за чего пункты несопоставимы и выбор между ними невозможен. Разведение по осям делает сценарии сравнимыми. Последовательность С0 → С1 → С2 выбрана потому, что каждый шаг оплачивает следующий и одновременно даёт данные для него, а первая поставка бьёт в боль, инвариантную для любого оператора (см. Р-026) |
| **Отклонённые альтернативы** | **С3 Платформа капекс-цикла** — необратимо помещает нас в категорию сравнения с Infovista; рынок автономных платформ планирования мал (Riaktr продана целиком за 10,4 млн евро); спор об атрибуции выручки нерешаем. Развивает Р-008. **С4 Сборка под одним экраном** как целостная конструкция — медленнее, а не быстрее (четыре переговорных процесса, четыре чужие дорожные карты), логику сверки всё равно пишем сами, а компания без собственного технологического актива оценивается как интегратор, не как продуктовая. Как принцип для краёв продукта сборка сохраняется по Р-003. **Г4 совместное предприятие с якорным оператором** — формально не отклонена, но помечена как критически опасная: усугубляет риск Ю1 и закрывает операторов-конкурентов региона |
| **Влияние** | Новый документ `02_Проектная_документация/07_Стратегические_развилки_и_сценарии.md` · мемо §5.3 · one-pager блок «Что выбираем с инвестором» · `00_Управление/Понятия/Ось_выбора_и_сценарий.md` · дорожная карта §2 |
| **Статус** | Принято как рамка. **Конкретный сценарий выбирается на гейте 0** по шести замерам базовой линии, а не сейчас |

## Р-026 · Шов между стандартами как главный структурный аргумент

| Поле | Значение |
|---|---|
| **Дата** | 27.07.2026 |
| **Инициатор** | Архитектор, по поручению владельца проверить отраслевые стандарты жизненного цикла |
| **Решение** | Ответом на вопросы «почему это не исправили до нас» и «какая боль встречается чаще всего» принимается **аргумент шва**: стадии 6–9 жизненного цикла (склад подрядчика · доставка на площадку · монтаж · ожидание включения) не покрыты **ни одним стандартом и ни одним классом систем**, потому что смежные стандарты по своему назначению останавливаются на границах этого участка |
| **Обоснование** | Проверка стандартов дала результат сильнее ожидаемого. Системы складского учёта заканчиваются на границе склада по назначению. ITU-T X.731 описывает только операционную жизнь объекта, уже присутствующего в сети. TMF639 формулирует прямо: инвентарь отражает «то, что уже предоставлено». IAS 16 требует признания при готовности к использованию, но не определяет, чем она подтверждается. Следствие: разрыв существует **по построению**, а не из-за качества управления. Значит, он инвариантен для любого оператора независимо от зрелости его систем и не может быть закрыт доработкой одной из сторон |
| **Отклонённые альтернативы** | Прежняя формулировка «разные владельцы данных, разная гранулярность» (мемо §2.6) верна, но описывает следствие, а не причину, и звучит как упрёк оператору. Сохранена как дополняющая, не как главная |
| **Влияние** | Мемо §2.8 и блок источников · one-pager блок «Почему это есть у каждого оператора» · `07_Стратегические_развилки_и_сценарии.md` §4 и §8 · `00_Управление/Понятия/Шов_между_стандартами.md` и `Жизненный_цикл_оборудования.md` · `03_Анализ_рынка/01_Рынок` §6.1 (усиление прежней формулировки «шов») |
| **Статус** | Принято |

## Р-027 · Правило записи файлов: после Edit — полная перезапись через Write

| Поле | Значение |
|---|---|
| **Дата** | 28.07.2026 |
| **Инициатор** | Архитектор, по итогам разбора порчи Word-версий |
| **Решение** | Файл, изменённый точечной правкой, **не считается пригодным для машинной обработки** (конвертация в Word, построение графа, любой скрипт), пока он не перезаписан целиком или не выгружен зеркалом в новый файл. Word и граф собираются только из зеркал в `_sync/`, проверенных сверкой числа заголовков |
| **Обоснование** | Установлено экспериментом 28.07.2026. Точечная правка доносит до вспомогательной среды **обрезанную** копию файла, и повторные правки её не обновляют. Создание нового файла доносит содержимое полностью. Проверка на всём пакете: обрезаны ровно 7 файлов — те, что правились точечно; 26 остальных целы. Именно это, а не «новая сессия» или «случайный сбой», испортило восемь Word-версий 26.07.2026 |
| **Отклонённые альтернативы** | «Пересобрать в новой сессии» — не работает: обрезка сохраняется. Повторная точечная правка того же файла — не работает: размер копии не меняется. Перезапись поверх существующего файла средствами среды — невозможна, доступ только на чтение |
| **Влияние** | Карта связей §1 и §5 · Вики_протокол §6 · скилл `assetloop-docs` · папка `_sync/` |
| **Статус** | Принято и проверено: три Word-файла собраны и верифицированы 28.07.2026 |

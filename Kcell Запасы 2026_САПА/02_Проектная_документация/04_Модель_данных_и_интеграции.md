## 1. Основные сущности

### 1.1. Номенклатурная позиция — справочные данные

Основа всего. Без единого справочника любые сверки дают мусор.

| Поле | Тип | Комментарий |
|---|---|---|
| `код_позиции` | строка | Код в финансовой системе |
| `категория` | ссылка | Детальная категория |
| `мета_группа` | ссылка | Укрупнённая группа для управленческой отчётности |
| `класс_прослеживания` | А / Б / В / Г | **Определяет метод учёта.** См. раздел 1.2 |
| `производитель`, `модель`, `артикул` | строка | |
| `критичность_для_сети` | перечисление | Влияние отказа на доступность услуги |
| `дата_снятия_с_производства` | дата | Планирование замен |
| `дата_снятия_с_поддержки` | дата | Планирование запаса |

### 1.2. Классы прослеживания

| Класс | Что относится | Заводской серийник | Виден в сети | Метод | В первой версии |
|---|---|---|---|---|---|
| **А — активное серийное** | Базовые блоки, радиомодули, маршрутизаторы, коммутаторы | Да | **Да** | Экземпляр + автосверка с сетевой системой | Да, первый |
| **Б — пассивное серийное** | Антенны, шкафы, выпрямители, батареи | Обычно да, но не читается в сети | Нет | Экземпляр + метка на приёмке + фото | Да, второй |
| **В — пассивное несерийное штучное** | Кронштейны, грозозащита, джамперы | Нет | Нет | Партия + подтверждение по комплекту | Нет |
| **Г — расходное измеряемое** | Фидер, кабель, крепёж, метизы | Нет | Нет | Норматив на площадку с допуском | **Не автоматизировать** |

**Классы А и Б дают 80–90% стоимости при 10–20% позиций** [оценка]. Классификация делается до архитектуры.

### 1.6. Доказательство — отдельная сущность

`идентификатор`, `тип` (документ · фотография · сигнал из сети · скан метки · подпись), `носитель` (ссылка на объектное хранилище), **`хеш`**, `время_создания`, `координаты`, `автор`, `признак_повторного_использования`.

> **Почему отдельная сущность, а не поле в событии:** аудитор проверяет не событие, а его основание. Хеш обязателен — доказательство должно быть неизменяемым, иначе оно не доказательство. Проверка на повторное использование фотографий закрывает риск К8 (подмена фотодоказательств).

### 1.7. Держатель

`идентификатор`, `тип` (склад оператора · подрядчик · бригада · площадка · ремонтный центр · транзит · утилизатор), `наименование`, `материально_ответственное_лицо`, `договор`, `лимит_выдачи`, `текущее_расхождение`, `статус_блокировки`.

> **Держатель — сущность, которой нет ни в одной системе оператора в явном виде.** Финансовая система знает материально ответственное лицо, складская — место хранения, но вопрос «у кого физически находится этот экземпляр прямо сейчас» не имеет владельца. Это и есть контур подрядчика.

### 1.8. Площадка

`идентификатор`, `координаты`, `проект_строительства`, `статус_строительства`, `идентификатор_в_сетевой_системе`, `дата_первого_включения_в_работу`, `дата_приёмки_актом`, `дата_ввода_в_основные_средства`, `подрядчик`.

**Три последние даты — предмет модуля 4 (контроль учётного признания).** Разрыв между первой и третьей и есть измеряемая проблема.

### 1.9. Расхождение

`идентификатор`, `тип`, `объекты[]`, `дата_выявления`, `сумма_влияния`, `приоритет`, `ответственный`, `срок_разбора`, `гипотеза_причины`, `решение`, `дата_закрытия`, `документ_основание`.

Типы расхождений: призрак · не на учёте · зависло у подрядчика · **работает в сети без основных средств** · конфликт локации · устаревшее подтверждение · превышение норматива · конфликт стоимости.

### 1.10. Потребность

`идентификатор`, `источник_плана`, `площадка`, `код_позиции`, `количество_требуется`, `срок`, `покрыто_складом`, `покрыто_возвратом`, `покрыто_перераспределением`, `покрыто_восстановленным`, **`к_закупке`**, `расчёт_покрытия`, `сигнал` (🔴/🟡/🟢), `статус_согласования`.

> Поле `к_закупке` — это продукт модуля 1 (шлюз покрытия) в одном числе. Всё остальное — обоснование.

### 1.11. Заказ на работу и материальный лист

**Заказ на работу:** `идентификатор`, `номер_у_подрядчика`, `площадка`, `подрядчик`, `бригада`, `тип_работ`, `плановая_дата`, `статус`, `ссылка_на_проектную_спецификацию`.

**Материальный лист** (строки заказа): `заказ`, `код_позиции`, `количество_плановое`, `количество_выданное`, `количество_подтверждённое_фото`, `количество_подтверждённое_сетью`, `количество_смонтированное_по_документам`, `расхождение`.

**Зачем нужен.** Заказ на работу — точка, в которой бригада получает контекст, ничего не вводя вручную. Она выбирает номер заказа, система подтягивает материальный лист, бригаде остаётся только сфотографировать. Без этого механизма полевой ввод превращается в набор данных руками и саботируется в первую неделю.

### 1.12. Проектная спецификация

`идентификатор`, `площадка`, `автор` (планировщик), `дата_обследования_локации`, `строки[]` (код позиции, количество).

**Зачем нужна.** Для несерийной и расходной номенклатуры (классы В и Г) проектная спецификация заменяет общий норматив «штук на площадку» точным расчётом по конкретной локации. Планировщик после обследования определяет, сколько именно кронштейнов, грозозащиты, фидера и крепежа нужно на этой площадке. Этот расчёт становится материальным листом и одновременно ожидаемым составом, с которым сверяется фактически выданное и смонтированное.

Общий норматив «штук на площадку» остаётся, но применяется только там, где проектной спецификации нет.

### 1.13. Сверка подрядчика

`идентификатор`, `подрядчик`, `период`, `выдано`, `смонтировано_подтверждено`, `возвращено_на_склад`, `остаток_на_площадке`, `демонтаж_возвращён`, **`расхождение`**, `допуск`, `статус` (в пределах допуска · превышение · заблокировано), `удержание_из_акта`.

## 2. Связи

```
Номенклатурная позиция ──1:N── Экземпляр актива ──1:N── Событие
        │                            │                      │
        │                            │                      └──N:1── Доказательство
        ├──1:N── Партия              ├──1:N── Расхождение
        ├──1:N── Потребность         ├──N:1── Держатель
        └──1:N── Норматив            ├──N:1── Площадка
                                     └──N:1── Экземпляр (родитель)

Площадка ──1:N── Проектная спецификация ──1:N── Строка спецификации
Площадка ──1:N── Заказ на работу ──1:N── Строка материального листа
Заказ на работу ──N:1── Держатель (подрядчик)
Строка материального листа ──N:M── Экземпляр актива / Партия
Держатель ──1:N── Сверка подрядчика
Площадка ──1:N── Потребность
```

**Ключевая связь, объясняющая механику продукта:** проектная спецификация задаёт ожидаемый состав площадки, заказ на работу с материальным листом связывает этот состав с конкретной бригадой и конкретной датой, а события с доказательствами показывают, что из ожидаемого действительно произошло. Расхождение между этими тремя слоями и есть предмет управления.

### 3.0. Ландшафт первого якорного клиента

У каждого оператора состав систем свой. У первого якорного клиента подтверждено следующее.

| Что есть | Что даёт продукту | Что нужно проверить |
|---|---|---|
| **Учётная система SAP:** складской, финансовый и бюджетный модули | Стоимость, движения, особый вид запаса у подрядчика, реестр основных средств, незавершённое строительство | Возможность выгрузки и её периодичность |
| **Система управления работами подрядчиков:** постановка задач, отслеживание статуса, формирование **актов ввода в эксплуатацию** и **заказов на работу** | **Готовый источник заказов на работу — механизм 1 не нужно строить с нуля, к нему нужно подключиться.** Плюс даты актов для расчёта лага документов | Есть ли программный интерфейс; содержит ли заказ материальный лист или только описание работ |
| **Проектная документация по площадкам:** дизайн-проекты и сметы в форматах Word, Excel, PDF | Проектные спецификации для классов В и Г — точный расчёт количества по конкретной локации | **Насколько единообразны формы.** Разбор неструктурированных документов — отдельная работа с непредсказуемой трудоёмкостью |
| **Системы управления сетью (OSS и система управления элементами сети)** | Активное оборудование, статус включения и выключения, серийный номер, локация, название площадки, код продукта | **Ключевой вопрос фазы 0:** сейчас эти данные «теоретически могут быть настроены». Нужно выяснить, отдаются ли серийные номера фактически, или требуется донастройка на стороне оператора |

**Три вывода из этого ландшафта.**

**Первый — хороший.** Механизм заказа на работу с материальным листом имеет готовый источник. Мы не строим систему постановки задач подрядчикам, а подключаемся к существующей. Это экономит месяцы и снимает сопротивление: подрядчик продолжает работать в привычном инструменте.

**Второй — требует проверки.** Готовность систем управления сетью отдавать серийные номера — не факт, а предположение. Формулировка «теоретически могут быть настроены» означает, что настройка ещё не сделана и потребует работы технического департамента. Это риск сроков, и он проверяется на первой неделе фазы 0.

**Третий — требует отдельного бюджета.** Проектная документация существует, но в виде файлов произвольной формы. Превращение её в структурированные проектные спецификации — это разбор документов, а не интеграция. Трудоёмкость зависит от единообразия форм и не может быть оценена до того, как мы увидим два-три десятка реальных документов.

### 3.1. Про сетевую систему отдельно

Это самая недооценённая по сложности интеграция и одновременно самая ценная.

**Почему начинать с неё:**
- доступ требует согласований с сетевым подразделением — это месяцы, а не дни;
- модели данных вендоров различаются, и унификация занимает время;
- именно она даёт бесплатное и практически не фальсифицируемое доказательство работы оборудования.

**Если технический департамент не даст доступ — экономика проекта проседает примерно вдвое.** Это выясняется на первой неделе, а не на четвёртом месяце.

**Запасной путь:** ручная выгрузка списка активных секторов раз в месяц. Хуже, но работает.

### 3.2. Про материал у подрядчика отдельно

Материал, переданный субподрядчику, в финансовой системе находится в особом виде запаса и **по определению не считается частью свободного запаса — именно поэтому планирование потребности его не учитывает** [факт]. Система сама признаёт, что не видит его.

Практическое следствие: выгрузка особого вида запаса — обязательный элемент фазы 0 и один из шести замеров базовой линии.

## 4. Правила разрешения конфликтов источников

Порядок применения сверху вниз; первое подходящее правило выигрывает.

| Код | Правило |
|---|---|
| **К1** | **Сигнал из сетевой системы имеет высший приоритет по вопросу «работает ли оборудование».** Это самое сильное и наименее фальсифицируемое доказательство |
| **К2** | Физическое наблюдение свежее 30 дней имеет приоритет над любым учётным утверждением по вопросу «где находится» |
| **К3** | Финансовая система имеет безусловный приоритет по стоимости, амортизации и принадлежности к балансу |
| **К4** | Складская система имеет приоритет по складским операциям при отсутствии более свежего физического наблюдения |
| **К5** | Автоматически зафиксированное наблюдение (сеть, скан метки) имеет более высокий уровень доверия, чем ручной ввод |
| **К6** | **При конфликте равных по свежести источников расхождение не разрешается автоматически**, а поднимается как объект с назначением владельца и срока разбора |

**Правило К6 принципиально.** Соблазн автоматически выбрать один источник уничтожает доверие к системе: пользователь один раз обнаруживает, что система молча переписала верные данные неверными, — и продукт мёртв.

## 5. Стандарты

| Стандарт | Применение |
|---|---|
| **TM Forum TMF639** — управление инвентарём ресурсов | Внешний интерфейс. Спецификация определяет стандартизированный механизм запроса и управления ресурсами инвентаря; физический ресурс описывается как тип ресурса с общим набором атрибутов |
| **TM Forum TMF634** — каталог ресурсов | Справочник спецификаций: номенклатура и мета-группы |
| **TM Forum ODA** — открытая цифровая архитектура | Общая архитектурная рамка отрасли |
| **IAS 2** — запасы | Учёт запасов, включая материал у подрядчика |
| **IAS 16** — основные средства | Момент готовности к использованию, капитализация |
| **IAS 36** — обесценение активов | Тесты на обесценение |
| **IFRS 16** — аренда | Сокращение складских площадей улучшает баланс, а не только отчёт о прибылях |
| **GS1** — стандарты кодирования | Метки и глобальная уникальность идентификаторов |
| **ISO/IEC 18000-6C** | Радиочастотные метки дальнего действия |

**Почему стандарты важны коммерчески, а не только технически:** если цель — внутренняя автоматизация, стандарты необязательны. Если цель — продукт для отрасли, первый же вопрос закупочного комитета оператора будет о соответствии TM Forum. Проектировать внешние интерфейсы сразу в этих терминах стоит недели; переделывать потом — кварталы.

## 6. Этапность интеграций

| Фаза | Интеграции | Обоснование |
|---|---|---|
| **Фаза 0** | Файловые выгрузки из финансовой, сетевой и складской систем | Запускается за дни без участия ИТ-департамента |
| **Фаза 1** | **Сетевая система (начинать первой)** + финансовая система + мобильное приложение | Минимально достаточный контур |
| **Фаза 2** | Складская система, справочник номенклатуры, закупочная система | Замыкание процесса |
| **Фаза 3** | Сервис компьютерного зрения | После накопления корпуса изображений |
| **Фаза 4** | Внешний интерфейс по TMF639/634, аналитический контур заказчика | Продуктизация |

**Тактическая рекомендация:** начинать всегда с файловых выгрузок, даже если программный интерфейс существует. Выгрузка запускается за неделю без участия ИТ-департамента; интерфейс требует квартала согласований. Первую ценность нужно показать до того, как начнётся интеграционный проект — иначе не будет мандата на интеграционный проект.

**Исключение — сетевая система.** Здесь наоборот: запрос доступа подаётся письменно на первой неделе, потому что согласование длится месяцы, а без него экономика проекта не складывается.
